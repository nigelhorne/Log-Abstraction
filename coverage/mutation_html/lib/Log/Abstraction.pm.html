  234: =head1 SYNOPSIS
  235: 
  236:   use Log::Abstraction;
  237: 
  238:   # The default level is 'warning'; 'trace' lets every example through
  239:   my $logger = Log::Abstraction->new(logger => 'logfile.log', level => 'trace');
  240: 
  241:   $logger->debug('This is a debug message');
  242:   $logger->info('This is an info message');
  243:   $logger->notice('This is a notice message');
  244:   $logger->trace('This is a trace message');
  245:   $logger->warn({ warning => 'This is a warning message' });
  246: 
  247:   # Structured fields
  248:   $logger->info('User logged in', { user_id => 42 });
  249: 
  250: =head1 DESCRIPTION
  251: 
  252: The C<Log::Abstraction> class provides a flexible logging layer on top of
  253: different types of loggers, including code references, arrays, file paths,
  254: and objects.  It also supports logging to syslog if configured.
  255: 
  256: =head2 Unicode
  257: 
  258: Messages may be character strings containing any Unicode text.  The file,
  259: fd and scalar-path backends write character strings as UTF-8 (unless an
  260: C<fd> handle already has a C<:utf8> or C<:encoding> layer, in which case the
  261: handle does the encoding), and C<format =E<gt> 'json'> output is UTF-8 too.
  262: journald fields are sent as UTF-8.  Byte strings are written unchanged.
  263: 
  264: =head2 Structured fields
  265: 
  266: Every logging method accepts a hash reference of structured fields after
  267: the message:
  268: 
  269:   $logger->info('User logged in', { user_id => 42, ip => $ip });
  270:   $logger->warn('Slow query', { ms => 1250 });
  271: 
  272: A hash reference is taken as fields only when it is the last of two or more
  273: arguments, so C<warn({ warning =E<gt> ... })> keeps its meaning, and a lone
  274: hash reference is still a message.  An empty hash reference is ignored.  The
  275: fields are copied, so changing the hash afterwards doesn't change what was
  276: logged.  They are kept out of the message and go to each backend as follows:
  277: 
  278: =over 4
  279: 
  280: =item * L</messages>, C<array> and an ARRAY C<logger> -- a C<fields> key in
  281: the entry, alongside C<level> and C<message>.
  282: 
  283: =item * a CODE C<logger> -- a C<fields> key in the hashref it is called with.
  284: 
  285: =item * C<format =E<gt> 'json'> -- a nested C<fields> object.  Objects are
  286: stringified; other references are kept as JSON data.
  287: 
  288: =item * C<journald> -- journal fields.  Each name is upper-cased, characters
  289: other than C<A-Z>, C<0-9> and C<_> become C<_>, leading underscores are
  290: removed and it is cut to 64 characters; a field left with no name is
  291: dropped.  Fields override the extra keys in the C<journald> hash, but never
  292: C<MESSAGE>, C<PRIORITY> or C<SYSLOG_IDENTIFIER>.
  293: 
  294: =item * text formats (C<file>, C<fd>, a scalar C<logger>), C<syslog>,
  295: C<sendmail> and object loggers -- appended to the message as logfmt-style
  296: C<key=value> pairs in key order, e.g. C<User logged in ip=10.0.0.1 user_id=42>.
  297: Characters other than C<[\w.-]> in a key become C<_>.  A value that is empty
  298: or contains white space, C<">, C<=> or C<\> is double-quoted, with C<"> and
  299: C<\> escaped and control characters written as C<\n>, C<\r>, C<\t> or
  300: C<\xNN>.  Objects are stringified and other references written as JSON.  An
  301: object logger is passed the pairs as an extra argument after the message.
  302: 
  303: =back
  304: 
  305: When logging through L<Log::Any>, a hash reference at the end of the call,
  306: together with the proxy's C<context>, arrives here as fields; see
  307: L<Log::Any::Adapter::Abstraction/structured>.
  308: 
  309: =head2 Per-backend level and format
  310: 
  311: Every backend can have its own C<level> and C<format>, as well as the
  312: logger's.  C<syslog>, C<journald> and C<sendmail> are hashes already, so
  313: they take them as keys.  C<file>, C<fd> and C<array>, inside a C<logger> hash
  314: or at the top level, may be given as a hash holding the destination under
  315: the backend's own name:
  316: 
  317:   my $log = Log::Abstraction->new(
  318:       level  => 'debug',
  319:       logger => {
  320:           file   => { file => '/var/log/myapp.log', format => 'json' },
  321:           fd     => { fd => \*STDERR, level => 'warning' },
  322:           array  => { array => \@recent, level => 'info' },
  323:           syslog => { level => 'error', format => '%level%: %message%' },
  324:       },
  325:   );
  326: 
  327: =over 4
  328: 
  329: =item * C<level> -- the backend only gets messages at this level or more
  330: severe.  A level name or a syslog number (0-7).  The logger's C<level> is
  331: applied first, so a backend's level can only narrow it: set the logger's
  332: C<level> to the most verbose any backend wants.
  333: 
  334: =item * C<format> -- a format string, or C<json>, as for the logger's
  335: L</format>, which it overrides.  For C<file> and C<fd> it is the line
  336: written.  For the others, which by default get the message as it is, it
  337: replaces the message: the C<array> entry's C<message>, the text sent to
  338: syslog, the journal's C<MESSAGE> field and the email body.
  339: 
  340: =back
  341: 
  342: The plain forms (C<file =E<gt> $path>, C<fd =E<gt> $handle>,
  343: C<array =E<gt> \@array>) still work and have no level or format of their
  344: own.  A blessed handle object is a destination, not the hash form.
  345: 
  346: =head2 File rotation
  347: 
  348: Log files written by path (a scalar C<logger>, a C<file> key in a C<logger>
  349: hash, and the top-level C<file>) can be rotated by size, by time, or both:
  350: 
  351:   my $log = Log::Abstraction->new(
  352:       file            => '/var/log/myapp.log',
  353:       rotate_size     => '10M',
  354:       rotate_interval => 'daily',
  355:       rotate_keep     => 7,
  356:   );
  357: 
  358: Before each write the file is checked, and if it is due it is renamed to
  359: F<myapp.log.1>, the old F<.1> to F<.2> and so on, the oldest beyond
  360: C<rotate_keep> being deleted; the line then goes to a new F<myapp.log>.  A
  361: rotation that fails (e.g. for lack of permission) is ignored, and the line is
  362: still written.  File handles passed as C<fd> aren't rotated.
  363: 
  364: Rotation isn't coordinated between processes: if several processes log to the
  365: same file, use B<logrotate> instead.
  366: 
  367: =head3 logrotate
  368: 
  369: The file is opened, appended to and closed for every message, never held
  370: open, so B<logrotate>'s default (rename the file and let the application
  371: create a new one) works without C<copytruncate>, and without sending the
  372: process a C<SIGHUP>: the next message is written to the new file.

  402: 
  403: =item * C<config_file>
  404: 
  405: Path to a configuration file (YAML, XML, INI, etc.) whose contents are
  406: merged with the constructor arguments.  On non-Windows systems the class
  407: can also be configured via environment variables prefixed with
  408: C<"Log::Abstraction::">.  For example:
  409: 
  410:   export Log::Abstraction::script_name=foo
  411: 
  412: =item * C<ctx>
  413: 
  414: Arbitrary context value passed through to CODE-ref logger callbacks as
  415: C<$args-E<gt>{ctx}>.
  416: 
  417: =item * C<format>
  418: 
  419: Format string for the file, fd and scalar-path backends; a backend's own
  420: C<format> (see L</Per-backend level and format>) overrides it for that
  421: backend.  Unset or an empty string means the default,
  422: C<%level%E<gt> [%timestamp%] %class% %callstack% %message%>.  Tokens expanded
  423: at log time:
  424: 
  425:   %callstack%   caller file and line number
  426:   %class%       blessed class of the logger object
  427:   %level%       upper-cased level name
  428:   %message%     the joined log message
  429:   %timestamp%   the time of the call; YYYY-MM-DD HH:MM:SS local time by
  430:                 default (see timestamp_format, timestamp_precision and utc)
  431:   %env_FOO%     value of $ENV{FOO}, or empty string if unset
  432: 
  433: Tokens are only expanded in the format string itself, never in the text
  434: of the message.  Each line break in a message is followed by a tab, so a
  435: continuation line can't be mistaken for a new log entry.
  436: 
  437: The special value C<"json"> (not a format string but a magic keyword) switches
  438: all file and fd backends to emit one compact JSON object per log line:
  439: 
  440:   {"timestamp":"...","level":"info","message":"...","file":"...","line":42}
  441: 
  442: This format is compatible with log aggregators such as journald, Loki,
  443: Elasticsearch, and Splunk.  C<class> is included when the logger is a subclass
  444: of C<Log::Abstraction>, and C<fields> when the call has L</Structured fields>.
  445: Keys are emitted in sorted order.
  446: 
  447: B<Security note:> because a format may contain C<%env_*%> tokens, which
  448: expand to environment variables, avoid granting untrusted sources write
  449: access to config files that set C<format> or any backend's C<format> (see
  450: L</Per-backend level and format>).
  451: 
  452: =item * C<level>
  453: 
  454: Minimum level at which to emit log entries.  Defaults to C<"warning">.
  455: Valid values (case-insensitive): C<trace>, C<debug>, C<info>/C<informational>,
  456: C<notice>, C<warn>/C<warning>, C<error>/C<err>, C<crit>/C<critical>/C<fatal>,
  457: C<alert>, C<emerg>/C<emergency>/C<panic>.  C<trace> and C<debug> are the same
  458: threshold (see L</LIMITATIONS>).  It may also be an array reference, whose
  459: first element is used, as some configuration-file formats produce.
  460: 
  461: =item * C<max_messages>
  462: 
  463: The most entries to keep in the in-memory history returned by
  464: L</messages>; when it is full, the oldest entry is discarded.  Must be a
  465: non-negative integer; C<0> keeps no history at all.  Unlimited by default, which in a long-running process
  466: means the history grows without bound.
  467: 
  468: =item * C<logger>
  469: 
  470: One of:
  471: 
  472: =over 4

 3027: =head1 LIMITATIONS
 3028: 
 3029: =over 4
 3030: 
 3031: =item B<Syslog hash mutation>
 3032: 
 3033: The C<syslog> sub-hash passed to C<new()> is mutated in-place on the first
 3034: log call: C<facility>, C<level> and C<format> are temporarily removed before
 3035: C<setlogsock()> is called, then restored; C<server> is permanently renamed
 3036: to C<host>.  Sharing a syslog hashref between two C<Log::Abstraction>
 3037: instances is not supported and produces undefined behaviour on the second
 3038: instance.
 3039: 
 3040: =item B<trace is the same threshold as debug>
 3041: 
 3042: syslog has no priority below debug, so C<trace> and C<debug> share one
 3043: threshold: a logger at C<debug> level also emits C<trace> messages, and
 3044: C<trace> can't be filtered separately.
 3045: 
 3046: =item B<Unbounded message history by default>
 3047: 
 3048: Every logged message is kept in the history returned by L</messages>.  In a
 3049: long-running process (a daemon, or under mod_perl) set C<max_messages> to
 3050: stop it growing without bound.
 3051: 
 3052: =item B<syslog connection is shared>
 3053: 
 3054: C<openlog()> and C<closelog()> act on the whole process, so every instance
 3055: logging to syslog shares one connection, opened with the C<script_name> of
 3056: the first.  It is closed when the last such instance is destroyed.
 3057: 
 3058: =item B<Structured fields are text in most backends>
 3059: 
 3060: Only the history, array, CODE-ref, JSON and journald backends keep
 3061: L</Structured fields> as data.  Text formats, syslog, email and object
 3062: loggers get them as C<key=value> text appended to the message, and a custom
 3063: C<format> has no token for them on their own.
 3064: 
 3065: =item B<Single-threaded email throttle>
 3066: 
 3067: The C<min_interval> throttle for the C<sendmail> backend and the
 3068: C<_syslog_opened> first-open flag are stored on the object without mutex
 3069: protection.  Under Perl ithreads or other concurrency models, objects shared
 3070: between threads are not safe.
 3071: 
 3072: =item B<OpenTelemetry not yet supported>
 3073: 
 3074: The OTel Logs SDK for Perl is incomplete; see the TODO block at the top of
 3075: F<lib/Log/Abstraction.pm> for a full status report and the list of blockers.
 3076: Monitor L<https://metacpan.org/pod/OpenTelemetry::SDK> for progress.
 3077: 
 3078: =item B<Log::Log4perl is a de-facto required dependency>
 3079: 
 3080: When no C<logger>, C<file>, C<fd> or C<array> backend is configured, C<new()>
 3081: loads L<Log::Log4perl> and uses it as the default backend, so it is a
 3082: required dependency even for applications that never use it.
