  233: =head1 SYNOPSIS
  234: 
  235:   use Log::Abstraction;
  236: 
  237:   # The default level is 'warning'; 'trace' lets every example through
  238:   my $logger = Log::Abstraction->new(logger => 'logfile.log', level => 'trace');
  239: 
  240:   $logger->debug('This is a debug message');
  241:   $logger->info('This is an info message');
  242:   $logger->notice('This is a notice message');
  243:   $logger->trace('This is a trace message');
  244:   $logger->warn({ warning => 'This is a warning message' });
  245: 
  246:   # Structured fields
  247:   $logger->info('User logged in', { user_id => 42 });
  248: 
  249: =head1 DESCRIPTION
  250: 
  251: The C<Log::Abstraction> class provides a flexible logging layer on top of
  252: different types of loggers, including code references, arrays, file paths,
  253: and objects.  It also supports logging to syslog if configured.
  254: 
  255: =head2 Unicode
  256: 
  257: Messages may be character strings containing any Unicode text.  The file,
  258: fd and scalar-path backends write character strings as UTF-8 (unless an
  259: C<fd> handle already has a C<:utf8> or C<:encoding> layer, in which case the
  260: handle does the encoding), and C<format =E<gt> 'json'> output is UTF-8 too.
  261: journald fields are sent as UTF-8.  Byte strings are written unchanged.
  262: 
  263: =head2 Structured fields
  264: 
  265: Every logging method accepts a hash reference of structured fields after
  266: the message:
  267: 
  268:   $logger->info('User logged in', { user_id => 42, ip => $ip });
  269:   $logger->warn('Slow query', { ms => 1250 });
  270: 
  271: A hash reference is taken as fields only when it is the last of two or more
  272: arguments, so C<warn({ warning =E<gt> ... })> keeps its meaning, and a lone
  273: hash reference is still a message.  An empty hash reference is ignored.  The
  274: fields are copied, so changing the hash afterwards doesn't change what was
  275: logged.  They are kept out of the message and go to each backend as follows:
  276: 
  277: =over 4
  278: 
  279: =item * L</messages>, C<array> and an ARRAY C<logger> -- a C<fields> key in
  280: the entry, alongside C<level> and C<message>.
  281: 
  282: =item * a CODE C<logger> -- a C<fields> key in the hashref it is called with.
  283: 
  284: =item * C<format =E<gt> 'json'> -- a nested C<fields> object.  Objects are
  285: stringified; other references are kept as JSON data.
  286: 
  287: =item * C<journald> -- journal fields.  Each name is upper-cased, characters
  288: other than C<A-Z>, C<0-9> and C<_> become C<_>, leading underscores are
  289: removed and it is cut to 64 characters; a field left with no name is
  290: dropped.  Fields override the extra keys in the C<journald> hash, but never
  291: C<MESSAGE>, C<PRIORITY> or C<SYSLOG_IDENTIFIER>.
  292: 
  293: =item * text formats (C<file>, C<fd>, a scalar C<logger>), C<syslog>,
  294: C<sendmail> and object loggers -- appended to the message as logfmt-style
  295: C<key=value> pairs in key order, e.g. C<User logged in ip=10.0.0.1 user_id=42>.
  296: Characters other than C<[\w.-]> in a key become C<_>.  A value that is empty
  297: or contains white space, C<">, C<=> or C<\> is double-quoted, with C<"> and
  298: C<\> escaped and control characters written as C<\n>, C<\r>, C<\t> or
  299: C<\xNN>.  Objects are stringified and other references written as JSON.  An
  300: object logger is passed the pairs as an extra argument after the message.
  301: 
  302: =back
  303: 
  304: When logging through L<Log::Any>, a hash reference at the end of the call,
  305: together with the proxy's C<context>, arrives here as fields; see
  306: L<Log::Any::Adapter::Abstraction/structured>.
  307: 
  308: =head2 Per-backend level and format
  309: 
  310: Every backend can have its own C<level> and C<format>, as well as the
  311: logger's.  C<syslog>, C<journald> and C<sendmail> are hashes already, so
  312: they take them as keys.  C<file>, C<fd> and C<array>, inside a C<logger> hash
  313: or at the top level, may be given as a hash holding the destination under
  314: the backend's own name:
  315: 
  316:   my $log = Log::Abstraction->new(
  317:       level  => 'debug',
  318:       logger => {
  319:           file   => { file => '/var/log/myapp.log', format => 'json' },
  320:           fd     => { fd => \*STDERR, level => 'warning' },
  321:           array  => { array => \@recent, level => 'info' },
  322:           syslog => { level => 'error', format => '%level%: %message%' },
  323:       },
  324:   );
  325: 
  326: =over 4
  327: 
  328: =item * C<level> -- the backend only gets messages at this level or more
  329: severe.  A level name or a syslog number (0-7).  The logger's C<level> is
  330: applied first, so a backend's level can only narrow it: set the logger's
  331: C<level> to the most verbose any backend wants.
  332: 
  333: =item * C<format> -- a format string, or C<json>, as for the logger's
  334: L</format>, which it overrides.  For C<file> and C<fd> it is the line
  335: written.  For the others, which by default get the message as it is, it
  336: replaces the message: the C<array> entry's C<message>, the text sent to
  337: syslog, the journal's C<MESSAGE> field and the email body.
  338: 
  339: =back
  340: 
  341: The plain forms (C<file =E<gt> $path>, C<fd =E<gt> $handle>,
  342: C<array =E<gt> \@array>) still work and have no level or format of their
  343: own.  A blessed handle object is a destination, not the hash form.
  344: 
  345: =head2 File rotation
  346: 
  347: Log files written by path (a scalar C<logger>, a C<file> key in a C<logger>
  348: hash, and the top-level C<file>) can be rotated by size, by time, or both:
  349: 
  350:   my $log = Log::Abstraction->new(
  351:       file            => '/var/log/myapp.log',
  352:       rotate_size     => '10M',
  353:       rotate_interval => 'daily',
  354:       rotate_keep     => 7,
  355:   );
  356: 
  357: Before each write the file is checked, and if it is due it is renamed to
  358: F<myapp.log.1>, the old F<.1> to F<.2> and so on, the oldest beyond
  359: C<rotate_keep> being deleted; the line then goes to a new F<myapp.log>.  A
  360: rotation that fails (e.g. for lack of permission) is ignored, and the line is
  361: still written.  File handles passed as C<fd> aren't rotated.
  362: 
  363: Rotation isn't coordinated between processes: if several processes log to the
  364: same file, use B<logrotate> instead.
  365: 
  366: =head3 logrotate
  367: 
  368: The file is opened, appended to and closed for every message, never held
  369: open, so B<logrotate>'s default (rename the file and let the application
  370: create a new one) works without C<copytruncate>, and without sending the
  371: process a C<SIGHUP>: the next message is written to the new file.

  390: 
  391: =over 4
  392: 
  393: =item * C<carp_on_warn>
  394: 
  395: If set to 1, and no C<logger> is given, call C<Carp::carp> on C<warn()>.
  396: Also causes C<error()> to C<carp> if C<croak_on_error> is not set.
  397: 
  398: =item * C<croak_on_error>
  399: 
  400: If set to 1, and no C<logger> is given, call C<Carp::croak> on C<error()>.
  401: 
  402: =item * C<config_file>
  403: 
  404: Path to a configuration file (YAML, XML, INI, etc.) whose contents are
  405: merged with the constructor arguments.  On non-Windows systems the class
  406: can also be configured via environment variables prefixed with
  407: C<"Log::Abstraction::">.  For example:
  408: 
  409:   export Log::Abstraction::script_name=foo
  410: 
  411: =item * C<ctx>
  412: 
  413: Arbitrary context value passed through to CODE-ref logger callbacks as
  414: C<$args-E<gt>{ctx}>.
  415: 
  416: =item * C<format>
  417: 
  418: Format string for the file, fd and scalar-path backends; a backend's own
  419: C<format> (see L</Per-backend level and format>) overrides it for that
  420: backend.  Unset or an empty string means the default,
  421: C<%level%E<gt> [%timestamp%] %class% %callstack% %message%>.  Tokens expanded
  422: at log time:
  423: 
  424:   %callstack%   caller file and line number
  425:   %class%       blessed class of the logger object
  426:   %level%       upper-cased level name
  427:   %message%     the joined log message
  428:   %timestamp%   the time of the call; YYYY-MM-DD HH:MM:SS local time by
  429:                 default (see timestamp_format, timestamp_precision and utc)
  430:   %env_FOO%     value of $ENV{FOO}, or empty string if unset
  431: 
  432: Tokens are only expanded in the format string itself, never in the text
  433: of the message.  Each line break in a message is followed by a tab, so a
  434: continuation line can't be mistaken for a new log entry.
  435: 
  436: The special value C<"json"> (not a format string but a magic keyword) switches
  437: all file and fd backends to emit one compact JSON object per log line:
  438: 
  439:   {"timestamp":"...","level":"info","message":"...","file":"...","line":42}
  440: 
  441: This format is compatible with log aggregators such as journald, Loki,
  442: Elasticsearch, and Splunk.  C<class> is included when the logger is a subclass
  443: of C<Log::Abstraction>, and C<fields> when the call has L</Structured fields>.
  444: Keys are emitted in sorted order.
  445: 
  446: B<Security note:> because a format may contain C<%env_*%> tokens, which
  447: expand to environment variables, avoid granting untrusted sources write
  448: access to config files that set C<format> or any backend's C<format> (see
  449: L</Per-backend level and format>).
  450: 
  451: =item * C<level>
  452: 
  453: Minimum level at which to emit log entries.  Defaults to C<"warning">.
  454: Valid values (case-insensitive): C<trace>, C<debug>, C<info>/C<informational>,
  455: C<notice>, C<warn>/C<warning>, C<error>/C<err>, C<crit>/C<critical>/C<fatal>,
  456: C<alert>, C<emerg>/C<emergency>/C<panic>.  C<trace> and C<debug> are the same
  457: threshold (see L</LIMITATIONS>).  It may also be an array reference, whose
  458: first element is used, as some configuration-file formats produce.
  459: 
  460: =item * C<max_messages>
  461: 
  462: The most entries to keep in the in-memory history returned by
  463: L</messages>; when it is full, the oldest entry is discarded.  Must be a
  464: non-negative integer; C<0> keeps no history at all.  Unlimited by default, which in a long-running process
  465: means the history grows without bound.
  466: 
  467: =item * C<logger>
  468: 
  469: One of:
  470: 
  471: =over 4
  472: 
  473: =item * A code reference -- called with a hashref C<{ class, file, line, level, message, ctx, fields }>
  474: (C<ctx> and C<fields> only when there are any)
  475:

 2891: 
 2892: =head2 CSV file logging for BI import
 2893: 
 2894: The code-reference backend gives you full control over the output format.
 2895: The example below writes every message at C<trace> level and above as a
 2896: CSV row to a file, producing output that can be loaded directly into a
 2897: spreadsheet or BI tool (Tableau, Power BI, Metabase, etc.).
 2898: 
 2899: Each row contains: C<timestamp>, C<level>, C<class>, C<file>, C<line>, C<message>.
 2900: 
 2901:   use Log::Abstraction;
 2902: 
 2903:   my $csv_file = 'app_events.csv';
 2904: 
 2905:   # Write the header row once (skip if the file already exists and has data).
 2906:   unless (-s $csv_file) {
 2907:       open my $fh, '>', $csv_file or die "Cannot open $csv_file: $!";
 2908:       print $fh qq{timestamp,level,class,file,line,message\n};
 2909:       close $fh;
 2910:   }
 2911: 
 2912:   # Helper: quote a single CSV field (escapes embedded double-quotes).
 2913:   my $csv_field = sub {
 2914:       my $v = defined $_[0] ? $_[0] : '';
 2915:       $v =~ s/"/""/g;
 2916:       return qq{"$v"};
 2917:   };
 2918: 
 2919:   my $logger = Log::Abstraction->new(
 2920:       level  => 'trace',        # capture everything from trace upwards
 2921:       logger => sub {
 2922:           my $args = $_[0];
 2923: 
 2924:           my $timestamp = POSIX::strftime('%Y-%m-%dT%H:%M:%SZ', gmtime);
 2925:           my $message  = join(' ', @{ $args->{message} // [] });
 2926: 
 2927:           open my $fh, '>>', $csv_file or return;
 2928:           print $fh join(',',
 2929:               $csv_field->($timestamp),
 2930:               $csv_field->($args->{level}),
 2931:               $csv_field->($args->{class}),
 2932:               $csv_field->($args->{file}),
 2933:               $csv_field->($args->{line}),
 2934:               $csv_field->($message),

 2987: =head1 LIMITATIONS
 2988: 
 2989: =over 4
 2990: 
 2991: =item B<Syslog hash mutation>
 2992: 
 2993: The C<syslog> sub-hash passed to C<new()> is mutated in-place on the first
 2994: log call: C<facility>, C<level> and C<format> are temporarily removed before
 2995: C<setlogsock()> is called, then restored; C<server> is permanently renamed
 2996: to C<host>.  Sharing a syslog hashref between two C<Log::Abstraction>
 2997: instances is not supported and produces undefined behaviour on the second
 2998: instance.
 2999: 
 3000: =item B<trace is the same threshold as debug>
 3001: 
 3002: syslog has no priority below debug, so C<trace> and C<debug> share one
 3003: threshold: a logger at C<debug> level also emits C<trace> messages, and
 3004: C<trace> can't be filtered separately.
 3005: 
 3006: =item B<Unbounded message history by default>
 3007: 
 3008: Every logged message is kept in the history returned by L</messages>.  In a
 3009: long-running process (a daemon, or under mod_perl) set C<max_messages> to
 3010: stop it growing without bound.
 3011: 
 3012: =item B<syslog connection is shared>
 3013: 
 3014: C<openlog()> and C<closelog()> act on the whole process, so every instance
 3015: logging to syslog shares one connection, opened with the C<script_name> of
 3016: the first.  It is closed when the last such instance is destroyed.
 3017: 
 3018: =item B<Structured fields are text in most backends>
 3019: 
 3020: Only the history, array, CODE-ref, JSON and journald backends keep
 3021: L</Structured fields> as data.  Text formats, syslog, email and object
 3022: loggers get them as C<key=value> text appended to the message, and a custom
 3023: C<format> has no token for them on their own.
 3024: 
 3025: =item B<Single-threaded email throttle>
 3026: 
 3027: The C<min_interval> throttle for the C<sendmail> backend and the
 3028: C<_syslog_opened> first-open flag are stored on the object without mutex
 3029: protection.  Under Perl ithreads or other concurrency models, objects shared
 3030: between threads are not safe.
 3031: 
 3032: =item B<OpenTelemetry not yet supported>
 3033: 
 3034: The OTel Logs SDK for Perl is incomplete; see the TODO block at the top of
 3035: F<lib/Log/Abstraction.pm> for a full status report and the list of blockers.
 3036: Monitor L<https://metacpan.org/pod/OpenTelemetry::SDK> for progress.
 3037: 
 3038: =item B<Log::Log4perl is a de-facto required dependency>
 3039: 
 3040: When no C<logger>, C<file>, C<fd> or C<array> backend is configured, C<new()>
 3041: loads L<Log::Log4perl> and uses it as the default backend, so it is a
 3042: required dependency even for applications that never use it.
