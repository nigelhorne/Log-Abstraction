  230: =head1 SYNOPSIS
  231: 
  232:   use Log::Abstraction;
  233: 
  234:   my $logger = Log::Abstraction->new(logger => 'logfile.log');
  235: 
  236:   $logger->debug('This is a debug message');
  237:   $logger->info('This is an info message');
  238:   $logger->notice('This is a notice message');
  239:   $logger->trace('This is a trace message');
  240:   $logger->warn({ warning => 'This is a warning message' });
  241: 
  242:   # Structured fields
  243:   $logger->info('User logged in', { user_id => 42 });
  244: 
  245: =head1 DESCRIPTION
  246: 
  247: The C<Log::Abstraction> class provides a flexible logging layer on top of
  248: different types of loggers, including code references, arrays, file paths,
  249: and objects.  It also supports logging to syslog if configured.
  250: 
  251: =head2 Unicode
  252: 
  253: Messages may be character strings containing any Unicode text.  The file,
  254: fd and scalar-path backends write character strings as UTF-8 (unless an
  255: C<fd> handle already has a C<:utf8> or C<:encoding> layer, in which case the
  256: handle does the encoding), and C<format =E<gt> 'json'> output is UTF-8 too.
  257: journald fields are sent as UTF-8.  Byte strings are written unchanged.
  258: 
  259: =head2 Structured fields
  260: 
  261: Every logging method accepts a hash reference of structured fields after
  262: the message:
  263: 
  264:   $logger->info('User logged in', { user_id => 42, ip => $ip });
  265:   $logger->warn('Slow query', { ms => 1250 });
  266: 
  267: A hash reference is taken as fields only when it is the last of two or more
  268: arguments, so C<warn({ warning =E<gt> ... })> keeps its meaning, and a lone
  269: hash reference is still a message.  An empty hash reference is ignored.  The
  270: fields are copied, so changing the hash afterwards doesn't change what was
  271: logged.  They are kept out of the message and go to each backend as follows:
  272: 
  273: =over 4
  274: 
  275: =item * L</messages>, C<array> and an ARRAY C<logger> -- a C<fields> key in
  276: the entry, alongside C<level> and C<message>.
  277: 
  278: =item * a CODE C<logger> -- a C<fields> key in the hashref it is called with.
  279: 
  280: =item * C<format =E<gt> 'json'> -- a nested C<fields> object.  Objects are
  281: stringified; other references are kept as JSON data.
  282: 
  283: =item * C<journald> -- journal fields.  Each name is upper-cased, characters
  284: other than C<A-Z>, C<0-9> and C<_> become C<_>, leading underscores are
  285: removed and it is cut to 64 characters; a field left with no name is
  286: dropped.  Fields override the extra keys in the C<journald> hash, but never
  287: C<MESSAGE>, C<PRIORITY> or C<SYSLOG_IDENTIFIER>.
  288: 
  289: =item * text formats (C<file>, C<fd>, a scalar C<logger>), C<syslog>,
  290: C<sendmail> and object loggers -- appended to the message as logfmt-style
  291: C<key=value> pairs in key order, e.g. C<User logged in ip=10.0.0.1 user_id=42>.
  292: Characters other than C<[\w.-]> in a key become C<_>.  A value that is empty
  293: or contains white space, C<">, C<=> or C<\> is double-quoted, with C<"> and
  294: C<\> escaped and control characters written as C<\n>, C<\r>, C<\t> or
  295: C<\xNN>.  Objects are stringified and other references written as JSON.  An
  296: object logger is passed the pairs as an extra argument after the message.
  297: 
  298: =back
  299: 
  300: When logging through L<Log::Any>, a hash reference at the end of the call,
  301: together with the proxy's C<context>, arrives here as fields; see
  302: L<Log::Any::Adapter::Abstraction/structured>.
  303: 
  304: =head2 Per-backend level and format
  305: 
  306: Every backend can have its own C<level> and C<format>, as well as the
  307: logger's.  C<syslog>, C<journald> and C<sendmail> are hashes already, so
  308: they take them as keys.  C<file>, C<fd> and C<array>, inside a C<logger> hash
  309: or at the top level, may be given as a hash holding the destination under
  310: the backend's own name:
  311: 
  312:   my $log = Log::Abstraction->new(
  313:       level  => 'debug',
  314:       logger => {
  315:           file   => { file => '/var/log/myapp.log', format => 'json' },
  316:           fd     => { fd => \*STDERR, level => 'warning' },
  317:           array  => { array => \@recent, level => 'info' },
  318:           syslog => { level => 'error', format => '%level%: %message%' },
  319:       },
  320:   );
  321: 
  322: =over 4
  323: 
  324: =item * C<level> -- the backend only gets messages at this level or more
  325: severe.  A level name or a syslog number (0-7).  The logger's C<level> is
  326: applied first, so a backend's level can only narrow it: set the logger's
  327: C<level> to the most verbose any backend wants.
  328: 
  329: =item * C<format> -- a format string, or C<json>, as for the logger's
  330: L</format>, which it overrides.  For C<file> and C<fd> it is the line
  331: written.  For the others, which by default get the message as it is, it
  332: replaces the message: the C<array> entry's C<message>, the text sent to
  333: syslog, the journal's C<MESSAGE> field and the email body.
  334: 
  335: =back
  336: 
  337: The plain forms (C<file =E<gt> $path>, C<fd =E<gt> $handle>,
  338: C<array =E<gt> \@array>) still work and have no level or format of their
  339: own.  A blessed handle object is a destination, not the hash form.
  340: 
  341: =head2 File rotation
  342: 
  343: Log files written by path (a scalar C<logger>, a C<file> key in a C<logger>
  344: hash, and the top-level C<file>) can be rotated by size, by time, or both:
  345: 
  346:   my $log = Log::Abstraction->new(
  347:       file            => '/var/log/myapp.log',
  348:       rotate_size     => '10M',
  349:       rotate_interval => 'daily',
  350:       rotate_keep     => 7,
  351:   );
  352: 
  353: Before each write the file is checked, and if it is due it is renamed to
  354: F<myapp.log.1>, the old F<.1> to F<.2> and so on, the oldest beyond
  355: C<rotate_keep> being deleted; the line then goes to a new F<myapp.log>.  A
  356: rotation that fails (e.g. for lack of permission) is ignored, and the line is
  357: still written.  File handles passed as C<fd> aren't rotated.
  358: 
  359: Rotation isn't coordinated between processes: if several processes log to the
  360: same file, use B<logrotate> instead.
  361: 
  362: =head3 logrotate
  363: 
  364: The file is opened, appended to and closed for every message, never held
  365: open, so B<logrotate>'s default (rename the file and let the application
  366: create a new one) works without C<copytruncate>, and without sending the
  367: process a C<SIGHUP>: the next message is written to the new file.

  386: 
  387: =over 4
  388: 
  389: =item * C<carp_on_warn>
  390: 
  391: If set to 1, and no C<logger> is given, call C<Carp::carp> on C<warn()>.
  392: Also causes C<error()> to C<carp> if C<croak_on_error> is not set.
  393: 
  394: =item * C<croak_on_error>
  395: 
  396: If set to 1, and no C<logger> is given, call C<Carp::croak> on C<error()>.
  397: 
  398: =item * C<config_file>
  399: 
  400: Path to a configuration file (YAML, XML, INI, etc.) whose contents are
  401: merged with the constructor arguments.  On non-Windows systems the class
  402: can also be configured via environment variables prefixed with
  403: C<"Log::Abstraction::">.  For example:
  404: 
  405:   export Log::Abstraction::script_name=foo
  406: 
  407: =item * C<ctx>
  408: 
  409: Arbitrary context value passed through to CODE-ref logger callbacks as
  410: C<$args-E<gt>{ctx}>.
  411: 
  412: =item * C<format>
  413: 
  414: Format string for the file, fd and scalar-path backends; a backend's own
  415: C<format> (see L</Per-backend level and format>) overrides it for that
  416: backend.  Tokens expanded at log time:
  417: 
  418:   %callstack%   caller file and line number
  419:   %class%       blessed class of the logger object
  420:   %level%       upper-cased level name
  421:   %message%     the joined log message
  422:   %timestamp%   the time of the call; YYYY-MM-DD HH:MM:SS local time by
  423:                 default (see timestamp_format, timestamp_precision and utc)
  424:   %env_FOO%     value of $ENV{FOO}, or empty string if unset
  425: 
  426: Tokens are only expanded in the format string itself, never in the text
  427: of the message.  Each line break in a message is followed by a tab, so a
  428: continuation line can't be mistaken for a new log entry.
  429: 
  430: The special value C<"json"> (not a format string but a magic keyword) switches
  431: all file and fd backends to emit one compact JSON object per log line:
  432: 
  433:   {"timestamp":"...","level":"info","message":"...","file":"...","line":42}
  434: 
  435: This format is compatible with log aggregators such as journald, Loki,
  436: Elasticsearch, and Splunk.  C<class> is included when the logger is a subclass
  437: of C<Log::Abstraction>, and C<fields> when the call has L</Structured fields>.
  438: Keys are emitted in sorted order.
  439: 
  440: B<Security note:> because C<format> may contain C<%env_*%> tokens, avoid
  441: granting untrusted sources write access to config files that set this key.
  442: 
  443: =item * C<level>
  444: 
  445: Minimum level at which to emit log entries.  Defaults to C<"warning">.
  446: Valid values (case-insensitive): C<trace>, C<debug>, C<info>/C<informational>,
  447: C<notice>, C<warn>/C<warning>, C<error>/C<err>, C<crit>/C<critical>/C<fatal>,
  448: C<alert>, C<emerg>/C<emergency>/C<panic>.  C<trace> and C<debug> are the same
  449: threshold (see L</LIMITATIONS>).
  450: 
  451: =item * C<max_messages>
  452: 
  453: The most entries to keep in the in-memory history returned by
  454: L</messages>; when it is full, the oldest entry is discarded.  Must be a
  455: non-negative integer.  Unlimited by default, which in a long-running process
  456: means the history grows without bound.
  457: 
  458: =item * C<logger>
  459: 
  460: One of:
  461: 
  462: =over 4
  463: 
  464: =item * A code reference -- called with a hashref C<{ class, file, line, level, message, ctx, fields }>
  465: (C<ctx> and C<fields> only when there are any)
  466: 
  467: =item * An object -- method matching the level name is called on it
  468: 
  469: =item * A hash reference -- may contain C<file>, C<array>, C<fd>, C<syslog>, C<journald>, and/or C<sendmail> keys,
  470: each of which may have its own C<level> and C<format> (see L</Per-backend level and format>)
  471: 
  472: =item * An array reference -- C<{ level, message }> hashrefs are pushed onto it, with a
  473: C<fields> key when the call has L</Structured fields>
  474: 
  475: =item * A scalar string -- treated as a file path to append to
  476: 
  477: =back
  478: 
  479: When not supplied, L<Log::Log4perl> is initialised as the default backend.

 2874: 
 2875: =head2 CSV file logging for BI import
 2876: 
 2877: The code-reference backend gives you full control over the output format.
 2878: The example below writes every message at C<trace> level and above as a
 2879: CSV row to a file, producing output that can be loaded directly into a
 2880: spreadsheet or BI tool (Tableau, Power BI, Metabase, etc.).
 2881: 
 2882: Each row contains: C<timestamp>, C<level>, C<class>, C<file>, C<line>, C<message>.
 2883: 
 2884:   use Log::Abstraction;
 2885: 
 2886:   my $csv_file = 'app_events.csv';
 2887: 
 2888:   # Write the header row once (skip if the file already exists and has data).
 2889:   unless (-s $csv_file) {
 2890:       open my $fh, '>', $csv_file or die "Cannot open $csv_file: $!";
 2891:       print $fh qq{timestamp,level,class,file,line,message\n};
 2892:       close $fh;
 2893:   }
 2894: 
 2895:   # Helper: quote a single CSV field (escapes embedded double-quotes).
 2896:   my $csv_field = sub {
 2897:       my $v = defined $_[0] ? $_[0] : '';
 2898:       $v =~ s/"/""/g;
 2899:       return qq{"$v"};
 2900:   };
 2901: 
 2902:   my $logger = Log::Abstraction->new(
 2903:       level  => 'trace',        # capture everything from trace upwards
 2904:       logger => sub {
 2905:           my $args = $_[0];
 2906: 
 2907:           my $timestamp = POSIX::strftime('%Y-%m-%dT%H:%M:%SZ', gmtime);
 2908:           my $message  = join(' ', @{ $args->{message} // [] });
 2909: 
 2910:           open my $fh, '>>', $csv_file or return;
 2911:           print $fh join(',',
 2912:               $csv_field->($timestamp),
 2913:               $csv_field->($args->{level}),
 2914:               $csv_field->($args->{class}),
 2915:               $csv_field->($args->{file}),
 2916:               $csv_field->($args->{line}),
 2917:               $csv_field->($message),
 2918:           ), "\n";
 2919:           close $fh;
 2920:       },
 2921:   );
 2922: 
 2923:   $logger->trace('application started');
 2924:   $logger->info('user logged in', { user => 'alice' });
 2925:   $logger->warn({ warning => 'disk usage above 80%' });
 2926: 
 2927: The resulting C<app_events.csv> looks like:
 2928: 
 2929:   timestamp,level,class,file,line,message
 2930:   "2026-05-27T14:00:00Z","trace","Log::Abstraction","app.pl","42","application started"
 2931:   "2026-05-27T14:00:01Z","info","Log::Abstraction","app.pl","43","user logged in"
 2932:   "2026-05-27T14:00:02Z","warn","Log::Abstraction","Log/Abstraction.pm","820","disk usage above 80%"
 2933: 
 2934: Note: C<class> is always C<Log::Abstraction> (or the subclass name if you subclass the
 2935: module).  For C<trace>, C<debug>, C<info>, and C<notice> calls, C<file> and C<line>
 2936: resolve to the caller's source location.  For C<warn> and C<error> calls the
 2937: extra C<_high_priority> stack frame shifts the resolution one level inward, so
 2938: C<file> and C<line> point into the module rather than the calling script.
 2939: 
 2940: For production use, consider replacing the manual C<$csv_field> quoting with
 2941: L<Text::CSV> for correct handling of embedded newlines and other edge cases.
 2942: 
 2943: If you also want real-time alerting on critical events, add the email logic
 2944: directly inside the code-ref callback -- test C<$args-E<gt>{level}> and call
 2945: your mailer for C<warn> / C<error> messages while still writing the CSV row
 2946: for every message.
 2947: 
 2948: Alternatively, use the C<sendmail> hash-ref backend on its own (without the
 2949: code-ref) and add a C<level> key to restrict emails to warn-and-above:
 2950: 
 2951:   my $logger = Log::Abstraction->new(
 2952:       level  => 'warn',
 2953:       logger => {
 2954:           sendmail => {
 2955:               host         => 'smtp.example.com',
 2956:               to           => 'ops@example.com',
 2957:               from         => 'logger@example.com',
 2958:               subject      => 'Application alert',
 2959:               level        => 'warn',   # only email at warn level and above
 2960:               min_interval => 300,      # at most one alert email per 5 minutes
 2961:           },
 2962:       },
 2963:   );
 2964: 
 2965: Note: the C<sendmail> backend writes the module's standard text format, not
 2966: CSV.  To produce CSV rows I<and> send email alerts from the same logger,
 2967: embed both the CSV-write and the mail-send logic inside a single code-ref
 2968: callback as described above.

 2970: =head1 LIMITATIONS
 2971: 
 2972: =over 4
 2973: 
 2974: =item B<Syslog hash mutation>
 2975: 
 2976: The C<syslog> sub-hash passed to C<new()> is mutated in-place on the first
 2977: log call: C<facility> and C<level> are temporarily removed before
 2978: C<setlogsock()> is called, then restored; C<server> is permanently renamed
 2979: to C<host>.  Sharing a syslog hashref between two C<Log::Abstraction>
 2980: instances is not supported and produces undefined behaviour on the second
 2981: instance.
 2982: 
 2983: =item B<trace is the same threshold as debug>
 2984: 
 2985: syslog has no priority below debug, so C<trace> and C<debug> share one
 2986: threshold: a logger at C<debug> level also emits C<trace> messages, and
 2987: C<trace> can't be filtered separately.
 2988: 
 2989: =item B<Unbounded message history by default>
 2990: 
 2991: Every logged message is kept in the history returned by L</messages>.  In a
 2992: long-running process (a daemon, or under mod_perl) set C<max_messages> to
 2993: stop it growing without bound.
 2994: 
 2995: =item B<syslog connection is shared>
 2996: 
 2997: C<openlog()> and C<closelog()> act on the whole process, so every instance
 2998: logging to syslog shares one connection, opened with the C<script_name> of
 2999: the first.  It is closed when the last such instance is destroyed.
 3000: 
 3001: =item B<Structured fields are text in most backends>
 3002: 
 3003: Only the history, array, CODE-ref, JSON and journald backends keep
 3004: L</Structured fields> as data.  Text formats, syslog, email and object
 3005: loggers get them as C<key=value> text appended to the message, and a custom
 3006: C<format> has no token for them on their own.
 3007: 
 3008: =item B<Single-threaded email throttle>
 3009: 
 3010: The C<min_interval> throttle for the C<sendmail> backend and the
 3011: C<_syslog_opened> first-open flag are stored on the object without mutex
 3012: protection.  Under Perl ithreads or other concurrency models, objects shared
 3013: between threads are not safe.
 3014: 
 3015: =item B<OpenTelemetry not yet supported>
 3016: 
 3017: The OTel Logs SDK for Perl is incomplete; see the TODO block at the top of
 3018: F<lib/Log/Abstraction.pm> for a full status report and the list of blockers.
 3019: Monitor L<https://metacpan.org/pod/OpenTelemetry::SDK> for progress.
 3020: 
 3021: =item B<Log::Log4perl is a de-facto required dependency>
 3022: 
 3023: When no C<logger>, C<file>, C<fd> or C<array> backend is configured, C<new()>
 3024: loads L<Log::Log4perl> and uses it as the default backend.  Although listed
 3025: as an optional runtime dependency, it is required in that default-backend
 3026: path.
